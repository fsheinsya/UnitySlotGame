# Slot（学園祭展示作品）

学園祭で展示した、Unity製のスロット（絵合わせ）ゲームです。
タイミングを合わせて3つのリールを止め、同じ絵柄を揃えることを目指します。

- 使用技術：Unity / C#

## 概要

3つのリールを回転させ、ボタンを押したタイミングでそれぞれ停止させるゲームです。
リールの停止位置制御と、絵柄の重み付き抽選を実装しています。

## 実装した主な機能

- しきい値方式による絵柄の重み付き抽選（7種の絵柄に出現率の傾斜をつけてリールを生成）
- リールの回転・停止位置制御（停止ボタンを押した後、絵柄がマスに揃う位置で停止）
- 停止ボタン・リトライボタン・効果音

## コードを読み返して見つけた設計上の問題

後から読み返すと、この時点では「動くものを作る」以上の設計意識がなかったことがよくわかります。

### 同じコードのコピー＆ペースト（Button1 / Button2 / Button3）

3つの停止ボタンが、呼び出すメソッド名（`stopReel` / `stopReel2` / `stopReel3`）が違うだけのほぼ同一クラスになっています。
リール番号を `SerializeField` で渡す1クラスにまとめれば、仕様変更が1ファイルの修正で済んだはずです。実際、効果音を追加したときに3ファイルへ同じ修正を繰り返しました。

### `GameObject.Find` による文字列依存の参照解決

`GameObject.Find("ReelController")` のようにオブジェクト名の文字列で参照を解決しているため、シーン上の名前を変えただけで実行時に壊れます。
コンパイル時に検出できないエラーを自分で仕込んでいる状態でした。`SerializeField` によるInspector注入に置き換えるべきでした。

### マジックナンバーの直書き

- 絵柄の間隔 `102.4f`
- リールのループ判定 `-9000f`
- 停止位置の判定しきい値 `0.87f〜0.92f`
- 絵柄の出現率テーブル（`div0`〜`div5`）

すべてコードに直接書かれており、バランス調整がそのままコード修正になっていました。停止判定のしきい値調整に時間がかかった原因の一つは、調整対象がコードの奥に埋まっていたことだと思います。

### フレームレート依存の移動処理

`Update()` 内の `Translate(0, speed, 0)` に `Time.deltaTime` を掛けていないため、リールの回転速度も停止判定も実行環境のFPSに依存します。展示PCでは意図通り動きましたが、環境が変われば挙動が変わるコードです。

### 責務の未整理

`ReelController` が `speed1/2/3`、`stopflag1/2/3` と3リール分の変数をベタ持ちしています。
「リール」を1つの単位（プレハブ＋クラス）として扱い、コントローラは配列で管理する構造の方が自然だったはずです。
